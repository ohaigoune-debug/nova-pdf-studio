# الأدوار والصلاحيات — PERMISSIONS

الحماية **في الخادم** دائماً: كل Server Action وكل Route Handler يستدعي `requireActor()` ثم يمرّر `Actor` للخدمة، والخدمة تتحقق بنفسها من الدور ومن `workspace_id`. الواجهة تُخفي الأزرار للراحة فقط.

## الأدوار

| الدور | الوصف | نطاق البيانات |
|---|---|---|
| `SUPER_ADMIN` | مالك المنصة | كل المساحات (workspaces) |
| `TEACHER` | أستاذ يملك مساحة | مساحته فقط (`workspace_id`) |
| `ASSISTANT` | مساعد أستاذ (ينضم بكود يولّده الأستاذ لبريده) | مساحة الأستاذ الذي يتبعه — الحضور/الغياب/السكانر/الحصص وقوائم الطلاب فقط |
| `STUDENT` | تلميذ | بياناته فقط + محتوى الأفواج المسجّل فيها |
| `PUBLIC` | زائر مسجّل بلا فوج | المحتوى العام فقط |
| `PARENT` | محجوز للمستقبل | — |

حالات الطالب داخل الفوج (`group_students.status`): `ACTIVE`, `SUSPENDED`, `SUSPENDED_DUE_TO_ABSENCE`, `INACTIVE`, `COMPLETED`, `LEFT_GROUP`. الطالب غير `ACTIVE` لا يستطيع توليد رمز حضور لذلك الفوج ولا يُحتسب في الغياب التلقائي.

## مساعد الأستاذ (ASSISTANT)

- **الانضمام**: الأستاذ يدخل بريد المساعد في `/teacher/assistants` فيحصل على كود `XXX-XXXX` (يُعرض مرة واحدة، يُحفظ hash فقط) ورابط `/assistant-join?code=…&email=…`. المساعد يفتح الرابط ويدخل الكود + **نفس البريد** + اسمه + كلمة سر ⇒ حساب بدور `ASSISTANT` وعضوية نشطة في `teacher_assistants` فوراً، وجلسة مفتوحة تحوّله إلى `/assistant`.
- **الكود مرتبط بالبريد**: بريد مختلف ⇒ `ASSISTANT_EMAIL_MISMATCH`. بريد يخص حساب طالب/أستاذ ⇒ `ASSISTANT_EMAIL_TAKEN`. مساعد نشط عند أستاذ آخر ⇒ `ASSISTANT_ALREADY_ACTIVE`. كود واحد نشط لكل بريد في المساحة (توليد جديد يعطّل السابق).
- **النطاق**: `Actor.workspaceId` للمساعد يُستخرج من العضوية النشطة فقط في `resolveActor`؛ لا يُقبل من المدخلات. عضوية واحدة نشطة لكل مستخدم (فهرس فريد جزئي).
- **الإلغاء**: `revokeAssistant` ⇒ `REVOKED` + إنهاء كل جلسات المساعد فوراً؛ أي جلسة جديدة تحمل `workspaceId = null` فتُرفض كل خدمات الحضور (`ASSISTANT_NO_WORKSPACE`) وتعرض لوحته شاشة "انتهت صلاحيتك". يمكن إعادة دعوته بكود جديد (نفس الحساب وكلمة السر).
- **الحرّاس**: `assertAttendanceStaff` + `inWorkspaceScope` في `assertSessionAccess` و`assertGroupStaffAccess` و`listSessions` و`listTeacherStudents` و`listStudentAttendance`؛ خدمات التصحيح/المحتوى/الأفواج/الأكواد/التبرير تبقى `assertRole('TEACHER','SUPER_ADMIN')`.

## قواعد العزل (Tenant Isolation)

1. كل سجل مملوك لأستاذ يحمل `workspace_id`.
2. `Actor` للأستاذ يحمل `workspaceId` ثابتاً من جدول `teachers`؛ لا يُقبل `workspaceId` من المدخلات أبداً.
3. الخدمات تستعمل `scopeWorkspace(actor)` الذي يرجع `workspace_id` إجبارياً للأستاذ، وللـSuper Admin يسمح بتمرير مساحة صريحة أو الكل.
4. الطالب لا يملك `workspace_id`؛ وصوله يُحدَّد عبر `group_students` (الفوج → المساحة).
5. `db/rls.sql`: سياسات RLS مكافئة على PostgreSQL (تُفعَّل مع `SET app.user_id / app.role / app.workspace_id` في كل معاملة) — طبقة ثانية للإنتاج على Supabase.

## اختبارات الصلاحيات (الحد الأدنى — موجودة في `tests/`)

- أستاذ لا يرى أفواج/طلاب أستاذ آخر.
- طالب لا يرى حضور/علامات طالب آخر.
- طالب غير ACTIVE لا يولّد رمز حضور.
- كود فوج A لا يعمل مع فوج B، ولا يُستعمل مرتين.
- علامة AI لا تُكتب فوق علامة الأستاذ دون اعتماد (المرحلة 6).
- مساعد أستاذ أ يمسح ويغلق حصص أستاذه فقط؛ حصة أستاذ ب ⇒ `SESSION_NOT_FOUND`؛ توليد أكواد/تبرير غياب/تصحيح ⇒ `FORBIDDEN`؛ بعد الإلغاء تُبطل جلساته (`tests/assistants.test.ts`).
