# الأدوار والصلاحيات — PERMISSIONS

الحماية **في الخادم** دائماً: كل Server Action وكل Route Handler يستدعي `requireActor()` ثم يمرّر `Actor` للخدمة، والخدمة تتحقق بنفسها من الدور ومن `workspace_id`. الواجهة تُخفي الأزرار للراحة فقط.

## الأدوار

| الدور | الوصف | نطاق البيانات |
|---|---|---|
| `SUPER_ADMIN` | مالك المنصة | كل المساحات (workspaces) |
| `TEACHER` | أستاذ يملك مساحة | مساحته فقط (`workspace_id`) |
| `STUDENT` | تلميذ | بياناته فقط + محتوى الأفواج المسجّل فيها |
| `PUBLIC` | زائر مسجّل بلا فوج | المحتوى العام فقط |
| `PARENT` | محجوز للمستقبل | — |

حالات الطالب داخل الفوج (`group_students.status`): `ACTIVE`, `SUSPENDED`, `SUSPENDED_DUE_TO_ABSENCE`, `INACTIVE`, `COMPLETED`, `LEFT_GROUP`. الطالب غير `ACTIVE` لا يستطيع توليد رمز حضور لذلك الفوج ولا يُحتسب في الغياب التلقائي.

## قواعد العزل (Tenant Isolation)

1. كل سجل مملوك لأستاذ يحمل `workspace_id`.
2. `Actor` للأستاذ يحمل `workspaceId` ثابتاً من جدول `teachers`؛ لا يُقبل `workspaceId` من المدخلات أبداً.
3. الخدمات تستعمل `scopeWorkspace(actor)` الذي يرجع `workspace_id` إجبارياً للأستاذ، وللـSuper Admin يسمح بتمرير مساحة صريحة أو الكل.
4. الطالب لا يملك `workspace_id`؛ وصوله يُحدَّد عبر `group_students` (الفوج → المساحة).
5. `db/rls.sql`: سياسات RLS مكافئة على PostgreSQL (تُفعَّل مع `SET app.user_id / app.role / app.workspace_id` في كل معاملة) — طبقة ثانية للإنتاج على Supabase.

## اختبارات الصلاحيات (الحد الأدنى — موجودة في `tests/`)

- أستاذ لا يرى أفواج/طلاب أستاذ آخر.
- طالب لا يرى حضور/علامات طالب آخر.
- طالب غير ACTIVE لا يولّد رمز حضور.
- كود فوج A لا يعمل مع فوج B، ولا يُستعمل مرتين.
- علامة AI لا تُكتب فوق علامة الأستاذ دون اعتماد (المرحلة 6).
